## Matt Pocock 工程技能建议

当当前项目任务与下列 Skill 的完整工作方式高度匹配时，主动向用户建议手动调用最合适的一项。这里只提供建议，不得因为语义匹配就自动调用、读取并执行这些 Skill 的专属流程；用户明确同意或显式调用后才使用。

- `ask-matt`：用户需要在多个工程方法、工作流或技术路线之间作判断，且希望获得工程顾问式建议。
- `grill-with-docs`：需求或设计仍需通过来回追问澄清，并希望把结论整理成项目文档；不是需求已经明确后的普通问答。
- `implement`：用户已认可一份具体 spec、计划或 ticket，并明确要求按它完成实现；普通小改动不因此自动推荐。
- `improve-codebase-architecture`：用户要求评估或系统性改善现有代码库架构；不用于常规单功能开发。
- `setup-matt-pocock-skills`：用户明确要在当前项目首次建立该工作流所需的 tracker、labels 或项目文档；不因进入新仓库而自动推荐。
- `to-spec`：讨论已形成足够稳定的需求，用户需要将其整理成正式、可验收的规格说明。
- `to-tickets`：spec 或实施方案已经获批，用户要把它拆解成有依赖关系、可执行的 tickets。
- `triage`：用户要对尚未分流的 issue、PR 或工作队列做分类、排序和处理决策；不用于已明确选定事项的直接实现。
- `wayfinder`：目标范围大、路径尚不清楚且跨多个阶段/会话，需要先建立决策与行动地图；不因任务看起来复杂就自动推荐。

只在匹配证据充分时建议，不按单个关键词触发；不适用时照常完成用户请求。每个工作阶段最多建议一项，只推荐最贴合当前阶段的 Skill，并用一句话说明原因、询问是否使用，然后等待用户选择。用户拒绝后立即按普通工作方式继续；同一阶段不重复建议。进入后续不同阶段时，可按同一规则建议另一项，但不得重复推销已拒绝的 Skill。用户已经明确点名或显式调用某项时，直接遵从，不再询问是否建议。

建议示例：“这一步是把已确认的方案拆成有依赖关系的任务，适合手动调用 `to-tickets`。要用它来处理吗？”不要同时列出多项让用户自行筛选。

手动调用方式取决于当前客户端；可提示用户使用客户端实际支持的 Skill 菜单或 `$skill-name` 显式调用。若当前客户端是否支持该 Skill 的手动调用尚未验证，明确说明未验证，不得声称菜单中一定可见或可用。上游 Skill 的 `disable-model-invocation` 与 `allow_implicit_invocation: false` 等限制必须保持不变；本建议规则不修改 Skill 文件、元数据或调用策略。
